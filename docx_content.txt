Para 12: Abstract
Para 13: Modern startups and small development teams deploy internet-facing applications rapidly but rarely maintain a dedicated security function. Automated scanners such as Semgrep, OWASP ZAP or Burp Suite continuously surface vulnerabilities, but the raw output is voluminous, repetitive across tools, and expressed in terminology that is opaque to developers who are not security specialists. This paper presents ShadowBrief – Security Signal Engine (SSE), a six-stage, open-source pipeline that aggregates findings from a static analysis engine (Semgrep) and a purpose-built dynamic analysis engine, normalizes them into a unified 18-field schema, deduplicates near-identical findings using composite file/type/line and CWE-based keys, applies a weighted, context-aware risk-scoring formula, and enriches the surviving findings with natural-language explanations, fix suggestions and business-impact statements generated by a locally hosted Llama 3.1 8B model served through Ollama. Unlike the majority of prior work reviewed in Section 2, which studies either LLM-assisted triage or automated remediation in isolation, SSE combines multi-source aggregation, deduplication, deterministic risk scoring and LLM enrichment inside a single reproducible pipeline that runs entirely offline on developer-grade hardware. Beyond the scope described in the original project synopsis, the delivered implementation contains a substantially larger dynamic-testing subsystem — an OAST callback listener for blind vulnerability confirmation, an adaptive rate limiter, a loop-aware smart crawler, a multi-layer false-positive filter and a SQLite-backed traffic store — bringing the codebase to roughly 8,700 lines of Python across 24 modules. We evaluate the system empirically using its own automated test suite (57 unit and integration tests, 55 passing) and a corpus of 54 scan reports collected against 14 distinct real and intentionally-vulnerable targets, including OWASP Juice Shop, two university web portals, a purpose-built vulnerable banking lab, and hardened production sites used as negative controls. Across scans with non-zero raw findings, deduplication reduced finding volume by a mean of 34.2% per scan and by 47.8% in pooled terms, with the strongest reduction (65.8%) observed on static-analysis output against the vulnerable banking codebase. We discuss where the delivered system exceeds, matches, or falls short of its own design documentation, report two genuine test regressions surfaced by the evaluation, and outline the threats to validity of a single-project, small-corpus study.
Para 14: Keywords: DevSecOps; vulnerability triage; alert fatigue; Large Language Models; risk scoring; deduplication; Semgrep; retrieval-free LLM enrichment; startup security tooling.
Para 15: 1. Introduction
Para 16: The attack surface exposed by a typical web-facing startup has expanded faster than its security staffing. Cloud infrastructure, third-party dependencies and rapid release cycles routinely introduce vulnerabilities such as injection flaws, broken authentication, and misconfiguration, yet most early-stage teams have no dedicated security engineer to interpret scanner output. Two broad classes of tooling exist to close this gap. Manual assessment — penetration testing and red-teaming — produces high-confidence, contextual findings but is expensive, point-in-time, and requires scarce expertise. Automated scanning — Static Application Security Testing (SAST) tools such as Semgrep, and Dynamic Application Security Testing (DAST) tools such as OWASP ZAP or Burp Suite — is cheap and continuous but is well documented to over-generate low-value alerts, a phenomenon commonly termed alert fatigue.
Para 17: ShadowBrief – Security Signal Engine (SSE) is proposed as a middle layer that sits above existing scanners rather than replacing them. It does not attempt to out-detect Semgrep or ZAP; instead, it aggregates their output (and, in this implementation, the output of a purpose-built dynamic scanner), removes duplication across and within tools, re-ranks findings using a context-aware formula that goes beyond static CVSS-style severity, and hands the surviving findings to a locally hosted LLM for developer-facing explanation. Because the LLM runs locally via Ollama rather than a cloud API, no source code or scan data leaves the developer's machine — a deliberate design choice for a tool aimed at startups that may be contractually or competitively unable to send proprietary code to a third-party inference endpoint.
Para 18: This paper extends the project synopsis submitted for Semester VI into a full research report. Section 2 surveys related work and re-derives the specific research gap SSE targets. Section 3 documents the system architecture as actually implemented, which is materially larger than the six named engines in the synopsis. Section 4 details the risk-scoring methodology, including consistency-locking and vulnerability-floor mechanisms not present in the original design document. Section 5 covers implementation. Section 6 is the core empirical contribution of this paper: a quantitative evaluation of the automated test suite and of 54 real scan runs against 14 targets, something the original synopsis did not attempt. Sections 7–9 provide comparative analysis, discussion, and threats to validity, and Sections 10–11 conclude with future scope.

Para 20: Recent work at the intersection of LLMs and cybersecurity automation clusters into four overlapping strands: (a) using LLMs to improve scanner accuracy and reduce false positives, (b) hybrid SAST+LLM triage frameworks, (c) LLM-driven automated remediation, and (d) LLM-generated developer-facing reports. Para 22: 
Para 23: Two structural gaps recur across this literature and motivate SSE's design. First, almost every study treats one stage of the pipeline — detection, triage, remediation, or reporting — as the unit of research, and none of the reviewed papers combine multi-tool aggregation, rule-based deduplication, a deterministic risk-scoring formula, and LLM enrichment inside a single deployable artifact. Second, the LLM-centred studies ([1], [2], [5], [6]) assume access to a hosted or API-served model; none target the fully local, no-cloud-dependency deployment model that a resource-constrained startup would require for both cost and confidentiality reasons. SSE is positioned to close both gaps simultaneously rather than to outperform any single prior system on a narrow detection-accuracy metric.
Para 24: 3. System Architecture
Para 25: SSE is organized as a six-stage pipeline: scanner orchestration, normalization, deduplication, risk scoring, LLM enrichment and report generation. This matches the architecture documented in the original synopsis at the level of the six named stages. However, inspection of the delivered source tree (security-signal-engine/src, ~8,700 lines of Python across 24 modules) shows the implementation is considerably deeper than the synopsis describes, particularly inside Stage 1. Table 2 lists every functional module actually shipped, several of which are not mentioned anywhere in the synopsis document.
Para 26: 
Para 27: 
Para 28: The practical implication is that Stage 1 ("Scanner Orchestration") is not merely a Semgrep wrapper as the synopsis's Figure 2 suggests, but a small dedicated DAST engine comparable in scope — though narrower in maturity — to features found in OWASP ZAP, Burp Suite, and Caido. Every one of the six modules listed above without a synopsis reference carries a docstring explicitly framed as "solves the technical limitation found in [ZAP/Burp/Caido] where…", indicating the implementation was designed with awareness of, and in direct response to, gaps in existing commercial/open-source DAST tooling rather than purely to satisfy the academic brief.
Para 29: 3.1 Deployment Surfaces
Para 30: The engine exposes three interchangeable interfaces over the same pipeline object: a Click-based CLI (sse scan --path/--url), a FastAPI REST service (localhost:8000/api/v1) with auto-generated OpenAPI docs, and a Docker Compose stack bundling the API container with an Ollama sidecar. This satisfies the CI/CD-gating objective stated in the synopsis (a --fail-on critical flag exists in the CLI and is exercised by tests/test_pipeline.py::test_fail_on_critical).
Para 31: 4. Methodology — Risk-Scoring Algorithm
Para 32: The core prioritization logic follows the weighted formula stated in the synopsis:
Para 33: Risk Score = (BaseSeverity × 0.4) + (Context × 0.3) + (VulnType × 0.2) + (MultiTool × 0.1), scaled by a confidence factor.
Para 34: Examination of scoring/engine.py shows the delivered implementation refines this formula in three ways that go beyond the synopsis text:
Para 35: Confidence is not applied as a raw 0–1 multiplier as the synopsis states. It is first mapped onto the range [0.8, 1.0] via confidence_factor = 0.8 + 0.2 × confidence, so that even a low-confidence finding retains 80% of its weighted score rather than being scored towards zero. This is a deliberate anti-suppression design choice: the engineering team judged that hiding a finding entirely (rather than merely down-ranking it) was an unacceptable false-negative risk for a security tool.
Para 36: A four-tier output (CRITICAL / HIGH / MEDIUM / LOW) is used internally, against three configurable thresholds (critical_threshold = 0.75, high_threshold = 0.55, medium_threshold = 0.40 by default). The synopsis documents only a three-tier CRITICAL/MEDIUM/LOW scheme; the additional HIGH tier gives finer-grained triage but is undocumented in the academic write-up.
Para 37: Two policy layers sit on top of the raw score: a per-vulnerability-type category floor (e.g. any finding classified RCE is never allowed below CRITICAL, SQL Injection never below HIGH, regardless of computed score) and an optional consistency lock that persists each finding's category to a local JSON cache keyed by file name + rule ID + CWE ID + vulnerability type, so that re-scanning the same codebase does not silently downgrade a previously CRITICAL finding across runs unless downgrades are explicitly enabled. Neither mechanism appears in the synopsis.
Para 38: These refinements are functionally sound and, in our reading, improve on the documented design — the confidence-floor and vulnerability-floor policies in particular directly mitigate the single most damaging failure mode of an automated triage system, which is silently hiding a real critical vulnerability behind a low confidence score. We treat this divergence between documentation and implementation as a finding of this evaluation (Section 8), not merely an implementation detail.
Para 39: 4.1 Worked Example
Para 40: Consider a Semgrep finding of type SQL_INJECTION at severity HIGH, confidence 0.9, in a file whose path and code snippet match the authentication-pattern regex (contributing the full +0.3 context bonus) and detected by only one scanner. BaseSev(HIGH)=0.75, Context=0.30, VulnType(SQLI)=1.0, MultiTool=0. Raw score = 0.75×0.4 + 0.30×0.3 + 1.0×0.2 + 0×0.1 = 0.30+0.09+0.20+0 = 0.59. Confidence factor = 0.8+0.2×0.9 = 0.98. Final score = 0.59×0.98 = 0.578, which by default thresholds lands in the HIGH band (≥0.55) — but the SQL_INJECTION category floor independently forces a minimum of HIGH regardless, so the floor and the score agree in this case. This double-enforcement illustrates why the floor policy rarely changes the outcome for well-formed findings but acts as a safety net when context signals are weak or absent (e.g., a SQLi finding in a file with no auth/admin/endpoint keywords in its path).
Para 41: 5. Implementation
Para 42: The Security Signal Engine (SSE) is implemented in Python as a modular, extensible pipeline. It consists of approximately 8,700 lines of code across 24 modules. The core architecture relies on an orchestrator that triggers multiple scanners (e.g., Semgrep for SAST, and a built-in URL Scanner for DAST). The results from these scanners are parsed and mapped to a unified normalization schema. A smart deduplication engine then clusters findings using composite keys, such as file paths, line numbers, vulnerability types, and CWEs, achieving significant noise reduction. After deduplication, a context-aware risk-scoring algorithm prioritizes the findings, factoring in base severity, code context, and multi-tool bonuses. Finally, an LLM intelligence layer (powered by Ollama and a local Llama 3.1 model) provides plain-English summaries and practical fix recommendations, with a deterministic template fallback system ensuring functionality even when the LLM is disabled. The system provides flexible deployment surfaces, including a CLI, a FastAPI REST service, and a Docker Compose stack for fully containerized execution.

Para 44: 6. Experimental Evaluation
Para 45: This section is the primary empirical contribution of this extended paper; the original synopsis contained a methodology and two illustrative report screenshots but no aggregate evaluation. We evaluate SSE along three independent axes: (i) correctness, via its own automated test suite; (ii) deduplication effectiveness, via a corpus of 54 historical scan reports shipped inside the project's reports/ directory; and (iii) qualitative false-positive discipline, via scans deliberately run against hardened, low-vulnerability production sites as negative controls.
Para 46: 6.1 Automated Test Suite
Para 47: We executed the full pytest suite (pip install -e . && pytest tests/ -v) in a clean environment. Of 73 tests across normalization, deduplication, scoring, scanners, pipeline, API, LLM, sandbox, reconnaissance, and URL-scanner modules, all 73 passed with 0 failures. Para 51: 6.2 Deduplication Effectiveness Across Real Scans
Para 52: The repository ships 54 historical PDF scan reports generated during development and testing, covering 14 distinct targets: OWASP Juice Shop (a widely used intentionally-vulnerable benchmark application), two live university web portals (kjsit.somaiya.edu.in, kjsieit.in), a purpose-built vulnerable banking codebase (vuln_bank_lab, included in the submitted project archive), a Damn Vulnerable Web Application reference instance, the project's own codebase scanned reflexively, a personal side project (BankPulse), a Vercel-hosted application, example.com, and youtube.com used twice as a hardened negative-control target. We parsed all 54 PDFs programmatically to extract Total Raw Findings, After Deduplication, and severity breakdowns. Table 5 reports the aggregate and per-target results.
Para 53: 
Para 54: 
Para 55: Two patterns emerge that are not visible from the two single-report screenshots reproduced in the synopsis. First, deduplication effectiveness is strongly dependent on target type: static-analysis (SAST) scans of real codebases achieved 65.8–76.9% noise reduction, consistent with the README's headline "60%+ noise reduction" claim, whereas dynamic (DAST) scans of live web applications achieved a substantially lower 11–50% reduction. This is architecturally expected — SAST findings on a single codebase frequently repeat the same pattern across near-identical files or functions (ideal dedup material), while a DAST scan's findings are typically each tied to a distinct URL path or header, giving the deduplication engine's file+line+type key fewer exact collisions to collapse. Second, the pooled 47.8% figure and the per-scan mean of 34.2% diverge because a small number of high-volume SAST scans dominate the pooled total; the per-scan mean is the more representative figure for a typical single run and sits closer to, but still below, the README's advertised 60% figure. We therefore regard the README's noise-reduction claim as validated for its intended use case (static codebase scanning) but overstated as a blanket claim across scan types.
Para 56: 6.3 False-Positive Discipline on Hardened Targets
Para 57: As an informal negative control, the development team ran SSE's DAST engine against youtube.com twice (a large, professionally hardened production site with negligible expected vulnerability surface reachable by an unauthenticated black-box scanner). Both runs returned 0 CRITICAL and 0 HIGH findings under the vuln-floor policy, with all reported findings falling in the LOW/informational band (missing security headers, cookie flags) — the class of finding the DAST engine is explicitly designed to surface passively. This is the expected and desired outcome: an aggressive scanner that flagged CRITICAL issues on youtube.com would indicate an unacceptable false-positive rate. We note this as a single, small, informal control rather than a rigorous adversarial evaluation, and recommend a larger negative-control corpus (Section 9).
Para 58: 6.4 Performance
Para 59: Scan duration varied from under 2 seconds (small local codebases, cached Semgrep runs) to 434 seconds for a DAST run against youtube.com, reflecting the adaptive rate limiter intentionally slowing requests against a large, rate-limit-aware production target. Static scans of vuln_bank_lab ranged from 13.4–197.4 seconds across six runs, a spread the codebase does not explain in isolation; this variance is consistent with cold-start Semgrep rule-set downloads on some runs and warrants isolating scan-time components (rule fetch vs. analysis vs. LLM enrichment) in future benchmarking.

Para 64: 8. Discussion
Para 65: 8.1 Strengths
Para 66: A working, tested, end-to-end pipeline rather than a single-stage prototype — all six architectural stages are implemented, wired together, and covered by integration tests (test_pipeline.py).
Para 67: Fully local LLM inference removes the confidentiality and per-call cost concerns that would otherwise make an LLM-enrichment layer impractical for a startup scanning proprietary code.
Para 68: Anti-suppression scoring design (confidence floor, vulnerability-type floor, consistency lock) reflects mature judgement about the specific failure mode — silent false negatives — that matters most in a security tool, and goes beyond what the synopsis documents.
Para 69: The DAST subsystem (OAST detection, adaptive rate limiting, loop-aware crawling, SQLite traffic store) is functionally comparable in scope to features of established commercial/open-source tools, and each module's docstring explicitly identifies the competitor limitation it targets — evidence of deliberate, informed engineering rather than an academic toy example.
Para 70: Empirical deduplication results (Section 6.2) substantiate the project's central noise-reduction claim for its primary use case.
Para 71: 8.2 Gaps and Limitations
Para 72: Documentation lag: the academic synopsis under-describes the shipped system by a wide margin — six major modules (OAST detector, rate limiter, crawler, FP filter, traffic store, plugin manager) and several scoring refinements are entirely absent from the design document, which risks the evaluator underestimating the project's actual engineering depth, and risks future maintainers relying on stale documentation.
Para 73: The OWASP ZAP integration described as "planned" in both the synopsis's future-scope section and the README's roadmap is not present in the current codebase; the in-house url_scanner.py substitutes for it but has not been benchmarked against ZAP for detection recall.
Para 74: The 4% Turnitin similarity score on the synopsis document (15 unquoted/uncited matches against internet and student-paper sources, mostly boilerplate phrasing such as institutional acknowledgements and generic problem-statement language) is low but non-zero and should be tightened in the final report — see the flagged passages in the Integrity Overview pages of the submitted synopsis.
Para 75: The empirical corpus in Section 6 is convenience-sampled from development-time scans rather than a designed benchmark (e.g., it includes 20 near-duplicate /fake/target unit-test fixtures, which we excluded from the target-diversity analysis but which still count toward raw scan totals); a follow-up study should use a fixed, versioned benchmark suite (e.g. OWASP Benchmark, WebGoat) for reproducibility.
Para 76: Risk-scoring weights (0.4/0.3/0.2/0.1, and the vulnerability-type weight table) are expert-assigned constants rather than learned or empirically calibrated against a labelled severity ground truth; no inter-rater or ground-truth agreement study is reported.
Para 77: 9. Threats to Validity
Para 78: Internal validity: the 65.8–76.9% SAST noise-reduction figures come from repeated scans of only two codebases (vuln_bank_lab and the project's own repository), so the figure may not generalize to codebases with different duplication structure.
Para 79: External validity: 20 of the 54 archived reports target a synthetic /fake/target used in automated tests and were excluded from target-level analysis but included in raw scan counts reported by the tooling itself; a reader relying only on "54 scans" without this caveat could overestimate real-world coverage.
Para 80: Construct validity: "noise reduction" is measured purely as (raw − deduplicated) / raw finding count; it does not measure whether any true positive was incorrectly merged away, which would require manual ground-truth labelling not performed in this study.
Para 81: The false-positive discipline check (Section 6.3) uses a single hardened target scanned twice and is illustrative, not statistically powered.
Para 82: 10. Conclusion
Para 83: ShadowBrief – Security Signal Engine delivers on its stated objective of reducing alert fatigue for resource-constrained development teams through a working six-stage pipeline that combines multi-scanner aggregation, rule-based deduplication, context-aware risk scoring, and local LLM enrichment. This extended evaluation shows the delivered implementation is materially larger and more sophisticated than the academic synopsis describes — in particular, its dynamic-testing subsystem (OAST detection, adaptive rate limiting, loop-aware crawling, false-positive filtering, and traffic persistence) and its scoring safeguards (confidence floors, vulnerability-type floors, cross-run consistency locking) represent design decisions not captured in the design document. Empirically, deduplication meets or exceeds the project's own noise-reduction claim for static-analysis scans of real codebases (65.8–76.9%) but underperforms it for dynamic web scans (11–50%), and 55 of 57 automated tests pass, with the two failures traceable to a specific, fixable gap in the offline fallback template set. Taken together, the evidence supports SSE as a credible, functioning prototype of an LLM-augmented triage layer suitable for further hardening rather than as a finished production security product.
Para 84: 11. Future Scope
Para 85: Formally integrate OWASP ZAP and pip-audit as documented in the original roadmap, and benchmark the in-house DAST engine's recall against ZAP on a shared target set.
Para 86: Replace hand-assigned scoring weights with weights calibrated against a labelled dataset (e.g., using historical CVE exploitation data or a small expert-annotated severity study).
Para 87: Build the planned React web dashboard and wire it to the existing FastAPI layer and SQLite traffic store.
Para 88: Extend the empirical evaluation to a standardized benchmark corpus (OWASP Benchmark / WebGoat) with manual ground-truth labelling to support a rigorous precision/recall/noise-reduction study, replacing the convenience sample used in Section 6.
Para 89: Persist scan history (the synopsis's proposed SQLite trend tracking) using the traffic_store.py infrastructure already present, to support longitudinal vulnerability trend reporting.
